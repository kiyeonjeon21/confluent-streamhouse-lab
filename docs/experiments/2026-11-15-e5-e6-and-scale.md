## E5: an agent grounded in live context

Question: does the agent answer from data that just changed, how long does it take, and how does an external MCP client compare?

Method (`uv run lab bench e5 --offsets 0,5,15,30 --rounds 5 --seed 7`):

- Each cycle restores RA214 (`ra214-on-time`), waits until Lightning serves it as `ON_TIME`, then writes `ra214-delayed`.
  The delay changes the correct answer for a passenger landing at 14:50 from `OFFER1=RA226;OFFER2=RA232;HOTEL=Harbor Point Hotel` to `OFFER1=RA214;OFFER2=RA226;HOTEL=NONE`.
- After a shuffled offset of 0, 5, 15, or 30 seconds, measured from the moment the event statement reported `COMPLETED`, both agents run on the same task at once.
- The in-Flink agent is `AI_RUN_AGENT` over `rebooking_requests` (P-001 and P-002), with `rebooking_agent_log` as its system log table, so each run's tool and model calls can be counted.
- The external agent is Claude Code (`claude -p`) with the agent's prompt as its system prompt, the same model (`claude-sonnet-4-6`), built-in tools disabled, and only the engine's `getMetadata` and `queryData` tools.
- Each answer is classified as fresh (the post-change line), stale (the pre-change line), other, or missing (no offer line).
- In the same cycle, a poller records when Lightning first serves RA214 as `DELAYED`.

Raw: `results/e5/20261115T152543Z-e23119.jsonl` (both agents) and `results/e5/20261115T155046Z-a90ab3.jsonl` (Claude Code only, rerun).

| Agent | Runs | Fresh | Stale | Other | Missing | p50 | p95 | max | Tool calls per answer |
|---|---|---|---|---|---|---|---|---|---|
| In-Flink (2 passengers per run) | 20 | 40 of 40 | 0 | 0 | 0 | 18.4 s | 22.7 s | 22.9 s | 3 (all 40) |
| Claude Code, first run | 20 | 17 | 0 | 0 | 3 | 16.8 s | 20.4 s | 20.6 s | 2 to 5 |
| Claude Code, rerun | 20 | 20 | 0 | 0 | 0 | 15.8 s | 18.6 s | 20.3 s | 3 (all 20) |

- **Lightning already served the change when the agents started.** In all 40 cycles the first poll after the event returned `DELAYED`, 675 to 865 ms after the event statement reported `COMPLETED` (one query's round trip from Seoul). So offsets of 0 to 30 s could not separate fresh from stale here; every answer that had an offer line was fresh.
- **The three misses in the first Claude Code run were a harness artifact.** The engine also serves `listTopics`. Claude Code showed it to the model but did not allow it; when the model called it, Claude Code stopped and asked for permission ("Please grant permission to the `mcp__rtce` tools"). The in-Flink tool leaves `listTopics` out with `allowed_tools`. The rerun removed it from Claude Code's tool list (`--disallowedTools`), and all 20 answers were fresh.
- **Same model, same number of tool calls.** With the same two tools, both agents made three calls per answer: the in-Flink agent (from its system log, 3 `TOOL_CALL_REQUEST` and 3 `MODEL_RESPONSE` events for every one of 40 requests), and Claude Code (`getMetadata` twice and `queryData` once in every rerun).
- **Neither followed "Reply with exactly one line".** 0 of 40 in-Flink answers and 2 of 20 rerun answers were a single line; the rest put a sentence of reasoning before the offer line.
- **Latency:** the in-Flink run includes snapshot start-up and answers two passengers in one statement; Claude Code's includes process start-up and answers one.
- **Cost:** Claude Code reported $0.717 and $0.697 for its 20-run sets, about $0.035 per answer. The in-Flink agent's inference shows up on the Confluent invoice by day only.

## E6: failure and change

Raw: `results/e6/` (one file per scenario). Bench pipeline only, except the connection scenario.

### Deleting the agent's MCP connection mid-run

`uv run lab bench e6 --scenario connection` (16:08 UTC):

| Time | Step | Result |
|---|---|---|
| +0 s | Agent run starts | |
| +5 s | `rtce-connection` deleted | |
| +23 s | That run finishes | Both answers correct, 27.3 s |
| +24 s | New run without the connection | Statement FAILED in 0.9 s: "Agent '`river-air-lab`.`river-air`.`rebooking_agent`' does not exist." |
| +31 s | Connection recreated with the same name | |
| +54 s | New run | Both answers correct, 22.7 s, with no change to the agent, tool, or model |

The error names the agent, but the agent was never dropped; recreating only the connection fixed it.

### Stopping and resuming the materialized table

`uv run lab bench e6 --scenario stop-resume` (16:41 to 16:45 UTC), with three writes to the probe flight while stopped:

- Stop request to `STOPPED`: 1.8 s.
- While stopped (2.6 min), Lightning served each write to the source table, and served the derived table's old value throughout, with no status change on either Lightning Table.
- Resume request to `RUNNING`: 7.7 s. The last write reached Lightning 72.6 s after `RUNNING` (82 s after the resume request).
- No change was lost: risk counts matched the generator's prediction for the probe flight before the stop (63,670 / 21,306 / 15,024) and after the resume (63,637 / 21,339 / 15,024).

### Evolving it with CREATE OR ALTER

`uv run lab bench e6 --scenario evolve` with `sql/e6/evolve-bench-passenger-state.sql`, which adds `WHERE p.connecting_flight_id IS NOT NULL` (16:46 to 16:52 UTC):

- The first attempt repeated the original `DISTRIBUTED BY (passenger_id) INTO 1 BUCKETS` unchanged and failed: "Changing distribution of materialized table is not supported." Without the clause it succeeded.
- Version 1 to version 2 `RUNNING`: 15 s.
- **Zombie rows:** all 15,024 `NO_CONNECTION` rows, which the new query no longer produces, were still in the output topic (Flink snapshot count) and in Lightning 2 minutes later, as the documentation says for upsert mode.
- **Existing keys stopped updating.** The probe flight's new time reached Lightning's source table (16:11), but the probe passenger's derived row still showed the old arrival (14:33) 6 minutes later. The new version starts with empty state and reads the sources from where the old one stopped, so it never saw the itineraries written earlier and has nothing to join a flight change with.
- A passenger whose flights and itinerary were all written after the evolution appeared in Lightning in 14 s.

### A record that no reader can decode

`uv run lab bench e6 --scenario unreadable` (16:52 to 17:03 UTC): one record on `bench_flight_status` with a valid Avro key and the value `not avro: ...`, at partition 0, offset 2065. Tableflow was enabled on the topic with its default error handling (`SUSPEND`).

| Reader | Within | What it reported |
|---|---|---|
| The materialized table (Flink, default `error-handling.mode` = `fail`) | 30 s | `FAILED`: "Error while deserializing value from topic 'bench_flight_status', partition 0, offset 2065." |
| Lightning, `bench_flight_status` | - | `ACTIVE`; skipped the record; a valid write one minute later was served normally |
| Lightning, `bench_passenger_state` | - | `ACTIVE`, and stale from then on, because its producer had failed |
| Tableflow | 109 to 149 s | `FAILED`, suspended: "Tableflow encountered a malformed record at partition: 0 offset: 2065. Contact support if you need help resolving this." |

Recovery, by hand (17:04 to 17:14 UTC):

1. `ALTER TABLE bench_flight_status SET ('error-handling.mode' = 'log')` (`sql/e6/bench-flight-status-log-errors.sql`) completed.
   Resuming the failed table with `stopped = false` returned HTTP 304, because it was not stopped.
2. Stop, then resume: `RUNNING`, then `FAILED` again on the same offset about 2 minutes later. The dead letter table `error_log` had no rows.
3. `CREATE OR ALTER` back to the original query (version 3): `RUNNING` in 9 s and still `RUNNING` 70 s later. `error_log` still had no rows, so where the record went is not shown. As in the evolution above, the new version starts with empty state.
4. Tableflow: `confluent tableflow topic update bench_flight_status --error-handling SKIP` alone cleared the suspension; `PENDING`, then `RUNNING` within about 45 s.

### Freshness from us-east-1

Raw: `results/e1/20261115T155056Z-9faa2a.jsonl` (source topic) and `results/e1/20261115T155815Z-ea2427.jsonl` (derived state). The `revision` field in these two headers is empty because the EC2 copy had no `.git`; the code was `4ee33c0` plus the E1 `--read` option.

**A plain Kafka write, read from the source topic's Lightning Table** (`--read source`, 30 samples, `bench_flight_status`):
visible 5.41 to 5.80 s after the broker acknowledgement (p50 5.51 s), never before 5.07 s.
Queries took 56 to 118 ms, so the bounds are about 0.4 s apart.
The documentation says a Lightning Table updates within 100 ms of data arriving in its topic; for this topic and plain, non-transactional writes, it took about 5 seconds every time.
This matches the 3 to 7 s between commit and Lightning that E2 measured from Seoul.

**Derived state at 100,000 rows** (30 samples, jittered as before):
min 7.1 s, p50 42.8 s, p95 66.7 s, max 67.4 s, mean 41.0 s, resolution 0.35 to 0.42 s.
The medians and maxima match the 10,000-row runs from Seoul (p50 46.1 s and 44.3 s, max 67.6 s and 68.2 s), so neither table size nor client location moved freshness.
The minimum did move: 7.1 s here against 17 to 18 s in both earlier runs.
The earlier floor was where those 30 writes happened to fall relative to the commits, not a fixed cost: a write that lands just before a commit can be visible after the Flink sink flush, the commit, and Lightning's 5 seconds.
